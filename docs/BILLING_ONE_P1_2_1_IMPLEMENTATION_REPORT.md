## 1. FINDING ĐƯỢC REMEDIATION

- **Finding ID:** `FIND-P1.2-01` (Severity: **MEDIUM**)
- **Tiêu đề:** Direct Payment Idempotency Gap
- **Mô tả trong Closure Audit:**
  - Luồng đối soát sao kê ngân hàng (`bank_transactions`) đạt True Idempotency nhờ ràng buộc duy nhất `matched_payment_id` và kiểm tra `status === 'UNMATCHED'`.
  - Tuy nhiên, API thanh toán thủ công trực tiếp `POST /api/payments` và `POST /api/invoices/:id/payments` chưa có cơ chế kiểm tra `Idempotency-Key` hoặc kiểm tra fingerprint của payload. Nếu client retry do lỗi mạng chập chờn hoặc gửi lặp request thanh toán unapplied cash, hệ thống sẽ tạo ra 2 bản ghi payment unapplied trùng lặp, làm tăng sai dòng tiền.

## 2. ROOT CAUSE

1. Bảng `public.payments` không thể đặt ràng buộc `UNIQUE (reference)` toàn cục do dữ liệu lịch sử và các kịch bản test lặp đi lặp lại có nhiều giao dịch mang cùng reference (ví dụ `CP2-FINAL`, `CP2-PARTIAL`). Do đó, không thể dựa vào cột `reference` để chống trùng.
2. Thiếu bảng quản lý vòng đời Idempotency Key độc lập ở cấp độ cơ sở dữ liệu (`payment_idempotency_keys`).
3. Thiếu cơ chế băm dấu vân tay mật mã (cryptographic fingerprinting) đối với payload yêu cầu thanh toán để phân biệt giữa:
   - **Retry hợp lệ:** Cùng Idempotency Key, cùng dữ liệu thanh toán $\rightarrow$ Trả về kết quả thanh toán ban đầu (cached response) mà không tạo dòng tiền mới.
   - **Tái sử dụng Key sai trái (Payload Mismatch):** Cùng Idempotency Key nhưng thay đổi số tiền, khách hàng hoặc danh sách hóa đơn $\rightarrow$ Từ chối với lỗi `409 Conflict`.

## 3. THIẾT KẾ KIẾN TRÚC IDEMPOTENCY (DESIGN)

```
Client Request
      │ (Headers: Idempotency-Key: <key>)
      ▼
┌──────────────────────────────────────────────────────────┐
│                   PaymentService                         │
│                                                          │
│  1. Compute SHA-256 fingerprint of request payload       │
│  2. Acquire 64-bit advisory lock:                        │
│     pg_advisory_xact_lock(hashtext('idemp_payment'), $1) │
│                                                          │
│  3. Check public.payment_idempotency_keys:               │
│     ├── Exists & hash matches?                           │
│     │     └── RETURN cached response (HTTP 200, Replay)  │
│     ├── Exists & hash mismatch?                          │
│     │     └── THROW 409 IDEMPOTENCY_KEY_PAYLOAD_MISMATCH │
│     └── Not exists?                                      │
│           ├── Insert Payment & Allocations (P1.2 engine) │
│           ├── Persist key, hash, response payload        │
│           └── RETURN created response (HTTP 201)         │
└──────────────────────────────────────────────────────────┘
```

### Bảng mới: `public.payment_idempotency_keys`
```sql
CREATE TABLE IF NOT EXISTS public.payment_idempotency_keys (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    idempotency_key VARCHAR(255) NOT NULL,
    request_hash VARCHAR(64) NOT NULL,
    payment_id BIGINT REFERENCES public.payments(id) ON DELETE SET NULL,
    response_status INTEGER NOT NULL DEFAULT 201,
    response_body JSONB NOT NULL,
    created_by BIGINT REFERENCES public.users(id) ON DELETE SET NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT payment_idempotency_keys_key_unique UNIQUE (idempotency_key)
);
```

### Ràng buộc & Chỉ mục (Indexes):
- `payment_idempotency_keys_key_unique`: Đảm bảo cấp độ engine PostgreSQL tính duy nhất của Idempotency Key.
- `payment_idemp_key_idx`: B-Tree index phục vụ tìm kiếm nhanh theo key.
- `payment_idemp_pay_id_idx`: B-Tree index liên kết với bảng `payments`.
- `payment_idemp_created_idx`: B-Tree index hỗ trợ truy vấn và dọn dẹp theo thời gian.

### Phân quyền (Least Privilege):

## 5. API CHANGES

Cả 3 endpoints tạo thanh toán và phân bổ đều được nâng cấp:
1. **`POST /api/payments` (Thanh toán trực tiếp):**
   - Đọc `Idempotency-Key` từ header HTTP `Idempotency-Key` (hoặc `X-Idempotency-Key`, hoặc `req.body.idempotency_key`).
   - Nếu có key: chạy qua cơ chế kiểm tra và khóa transaction advisory lock.
   - Nếu là replay: Trả về HTTP 200 kèm `is_idempotent_replay: true`, không tăng Prometheus metric, không lặp audit log.
2. **`POST /api/invoices/:id/payments` (Thanh toán hóa đơn cụ thể):**
   - Hỗ trợ đầy đủ `Idempotency-Key`.
   - Replay request trả về cached invoice payment response mà không tăng thêm `paid_total`.
3. **`POST /api/payments/:id/allocations` & `POST /api/payments/allocate` (Phân bổ thanh toán):**
   - Hỗ trợ `Idempotency-Key` khi phân bổ dòng tiền Unapplied Cash sang nhiều hóa đơn.

## 6. IDEMPOTENCY SEMANTICS

- **Bất biến Dòng tiền:** 1 Idempotency Key = Tối đa 1 Dòng tiền thực nhận (1 Financial Effect).
- **Phát hiện Xung đột Payload (Fingerprint Mismatch):**
  - Hàm [computePaymentRequestFingerprint](file:///c:/Users/phamt/OneDrive/Desktop/Billing_One/app/src/services/paymentService.js#L14-L32) băm SHA-256 các trường: `customerId`, `invoiceId`, `amount`, `method`, `paidAt`, `reference`, và danh sách `allocations` đã được sắp xếp.
  - Nếu gửi lại cùng key với bất kỳ trường nào bị thay đổi $\rightarrow$ Lập tức ném `409 Conflict: IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`.
- **An toàn khi Thất bại (Rollback Safety):**
  - Vì bản ghi `payment_idempotency_keys` được insert trong cùng transaction với `payments`, nếu request gặp lỗi trước khi commit (ví dụ: validation error, hóa đơn không tồn tại), toàn bộ transaction rollback $\rightarrow$ Key không bị khóa lại, client được phép gửi lại request hợp lệ với cùng key đó (đã kiểm chứng tại Test 8).

## 7. CONCURRENCY STRATEGY

Để ngăn chặn tuyệt đối Race Condition khi 2 tiến trình client gửi cùng 1 Idempotency Key tại cùng một thời điểm chính xác:
1. **64-bit Transaction-level Advisory Lock:**
   ```sql
   SELECT pg_advisory_xact_lock(hashtext('idemp_payment'), hashtext($1));
   ```
   - Request A và B đến cùng lúc với cùng key:
     - Request A nhận được lock, kiểm tra thấy key chưa có trong DB $\rightarrow$ Tiến hành tạo Payment và lưu key.
     - Request B bị block chờ tại advisory lock.
     - Khi Request A commit, Request B được giải phóng $\rightarrow$ Kiểm tra thấy key đã có trong DB $\rightarrow$ So khớp hash thành công $\rightarrow$ Trả về kết quả cached từ Request A.
2. **Database-level Unique Constraint:**
   - Ràng buộc `payment_idempotency_keys_key_unique` bảo đảm tính toàn vẹn ngay cả khi có truy vấn từ các kết nối khác ngoài application logic.
